# PRD · 建任务来源必填项前后端口径对齐（关联决议项）

## 1. 背景与目标

### 1.1 现象（Lead 已复现，可原样执行）

前端 `http://localhost:5174` + 后端 `18081`（r5 修复版 jar，演示库 `supervise`，`admin / Supervise@2026`）。会议 1「11 月产品例会（Q4 交付冲刺）」有 5 条决议项，其中 4 条已转任务、1 条可关联。

任务池 → 新建任务 → 来源类型保持默认「会议决议」→ 填写标题、负责人、截止日期并选择来源会议 → 「关联决议项」留空（placeholder 明写「可不选，只关联会议」）→ 点击保存。

实际结果：服务端返回 `422 VALIDATION_FAILED`，`fieldErrors=[{"field":"sourceDecisionItemId","message":"请选择关联决议项"}]`；前端只把数量渲染成底部提示「还有 1 项需要修改」，字段旁没有任何文案，焦点也没有落到该字段——用户被要求「再改一项」，却找不到改哪里。

### 1.2 根因：同一份规则存在两套口径，表单层缺了一条

| 层 | 位置 | 现状 |
| --- | --- | --- |
| 后端（权威） | `server/src/main/java/com/pmo/supervise/task/TaskService.java:209-211` | `MEETING` 形态强制 `sourceMeetingId` 与 `sourceDecisionItemId` 均非空，缺失即 422「请选择关联决议项」 |
| 前端校验 | `web/src/components/task/TaskFormDrawer.vue:301-338` | `validate()` 只校验标题/负责人/截止日期，会议形态只校验 `meetingId`，完全不校验 `decisionItemId` |
| 前端字段 | `web/src/components/task/TaskFormDrawer.vue:513-521` | 「关联决议项」无 `required` 标记、无 `:invalid`/`:error` 绑定、也没有 `:ref` 包裹（对比 `meetingId` 在 `:500` 的包裹），placeholder 为「可不选，只关联会议」 |
| 前端接错 | `web/src/components/task/TaskFormDrawer.vue:362-373` | `applyServerErrors` 虽然经 `SERVER_FIELD_MAP`（`:357`）把 `sourceDecisionItemId` 映射到 `decisionItemId` 并写进 `errors`，但该字段不渲染错误、`fieldEls['decisionItemId']` 从未注册，于是只剩底部摘要 |

r1 PRD AC-6 已写明「来源会议 + 决议项：会议 id + 决议项 id，来源=会议决议时必填」，并要求「表单阻止提交并高亮缺失项并给出字段名」；r4 PRD AC-2 再次确认「会议型必须会议 + 决议项」。即后端与产品口径早已确定，本轮是**前端表单层没跟上**，不是规则要改。

### 1.3 目标

1. 「关联决议项」在会议形态下成为**真正的必填项**：有必填标记，`validate()` 拦截，错误就地展示，焦点落到字段——用户在点击保存的当下就知道该选什么，而不是等服务端 422。
2. **三形态口径逐项对齐**：`MEETING`（会议 + 决议项）、`PROJECT`（项目）、`NOTE`（1–200 字说明）的前端必填集合、字段映射、错误呈现与服务端 `validateSource()` 完全一致；服务端 422 仍然能定位到任一来源字段（不只决议项）。
3. **编辑态零回归**：来源只读逻辑、只提交标题/优先级的载荷、不因新增必填被拦截。
4. 补前端表单校验回归用例，让「空决议项不可提交」「服务端 422 能定位到字段」成为可重复执行的契约。

**成功标准**：按 1.1 的步骤，留空决议项点保存 → 不发 `POST /api/tasks`，字段下方出现「请选择关联决议项」且焦点在该下拉；选上第 5 条可关联决议项后保存 → `POST` 只发一次并成功，任务池可见、详情来源正确显示会议与决议项；编辑任一会议任务只改标题仍能保存。

## 2. 用户故事与验收标准

> AC 在本需求夹内从 AC-1 连续编号，是本次交付的验收契约；技术阶段需逐条给出实现与验证方式。

### US-1 作为管理员，我建会议任务时希望当场知道还缺「关联决议项」

**AC-1 会议形态必填可见、可拦截**
- 新建任务、来源形态为 `MEETING` 时：「关联决议项」标签带必填标记；placeholder 不含「可不选」；字段初始为空。
- 未选择决议项直接点保存：**不产生任何 `POST /api/tasks` 请求**；底部摘要显示「还有 1 项需要填写」；字段行内显示「请选择关联决议项」；焦点落在该下拉（jsdom 断言 `document.activeElement`，或断言被聚焦元素就是该字段容器内的可聚焦控件）。
- 必填标记、行内错误与焦点三者缺一即判失败——只把 placeholder 改掉不算交付。

**AC-2 选齐后一次提交成功**
- 选中一条可用决议项后保存：`POST /api/tasks` 恰好 1 次，状态 201；请求体 `sourceDecisionItemId` 为数字且等于所选 id，并同时带 `sourceMeetingId`；不出现 `422`，也不出现「选了却被清空」。
- 从决议项自动带出标题/负责人/截止日期的既有行为保持不变：用户已手填的字段不被覆盖（`TaskFormDrawer.vue:270-282` 的 `onDecisionItem` 语义）。

### US-2 作为管理员，我希望三种来源形态的必填要求一致，不靠试错

**AC-3 三形态「前端必填集合 = 服务端 validateSource()」逐项对齐**

| 形态 | 必填项 | 本地拦截文案（字段行内） | 提交时必须携带 | 提交时不得出现 |
| --- | --- | --- | --- | --- |
| `MEETING` | 来源会议 + 关联决议项 | 请选择来源会议 / 请选择关联决议项 | `sourceMeetingId`、`sourceDecisionItemId` | `sourceProjectId`、`sourceNote` |
| `PROJECT` | 来源项目 | 请选择来源项目 | `sourceProjectId` | `sourceMeetingId`、`sourceDecisionItemId`、`sourceNote` |
| `NOTE` | 来源说明 1–200 字 | 请填写来源说明… / 来源说明不超过 200 字 | `sourceNote`（去首尾空格） | `sourceMeetingId`、`sourceDecisionItemId`、`sourceProjectId` |

- 对每种形态构造「只缺该形态必填项」的表单：本地拦截、行内文案、焦点落位、0 次网络请求；再构造合法表单：载荷与该行「必须携带/不得出现」完全一致。
- 服务端对照点（只核对、不改）：`TaskService.java:205-258` 的 `MEETING`/`PROJECT`/`NOTE` 三分支；`CreateTaskRequest.java:22-45` 的 title 1–100、`sourceNote ≤200`、`ownerId`/`dueDate` 非空——前端 `TITLE_MAX=100`、`NOTE_MAX=200` 与之相等，本轮不得放宽或收紧任何一侧。

**AC-4 服务端 422 仍能定位到字段（兜底通路）**
- 以表格驱动覆盖四个来源字段：`sourceMeetingId → meetingId`、`sourceDecisionItemId → decisionItemId`、`sourceProjectId → projectId`、`sourceNote → note`。当 `taskApi.create` 以 422 返回对应 `fieldErrors` 时：底部摘要为「还有 N 项需要修改」（N = 返回的字段数），**每个字段行内显示服务端 message**，焦点落在首个错误字段。
- 反例即失败：只出现底部摘要、字段旁无文案、焦点停在抽屉顶部或保存按钮。

### US-3 作为管理员，编辑既有任务不应被新必填项干扰

**AC-5 编辑态来源只读零回归**
- 编辑 `MEETING`/`PROJECT`/`NOTE` 三种任务：来源区保持只读（来源类型为只读文本；会议/决议项/项目/说明为禁用控件或只读行），不出现「未满足的必填」提示。
- 只改标题或优先级点保存：`PUT /api/tasks/{id}` 恰好 1 次并成功，载荷**不含任何 `source*` 字段**；编辑态 `validate()` 不校验来源（保持 `TaskFormDrawer.vue:320` 的 `if (!isEdit.value)` 分支语义）。
- 会议任务的既有决议项在编辑态能正确回显（名称/描述可见），不得因为必填改造变成空白而让人误以为丢失。

### US-4 作为管理员，遇到「没有可选决议项」时我要立刻知道原因

**AC-6 决议项不可选的两类边界可解释**
- **无可选项**：所选会议的决议项全部已转任务（`decisionItems` 返回的项均 `converted=true` 或列表为空）时，字段行内给出「该会议暂无可关联的决议项（均已成任务），请改选会议或改用其他来源」；此时点保存按该原因提示，不产生 `POST`，不得只报「请选择关联决议项」让用户以为是自己漏选。
- **加载失败**：决议项请求失败时，字段行内给出「决议项加载失败」并提供可点击的重试（复用 `loadItems`，`TaskFormDrawer.vue:243-254`）；重试成功后列表可用。点保存时的提示与失败原因一致，不产生 `POST`。
- 决议项加载中（`itemsLoading`）点保存：提示等待加载完成，不误判为「未选择」。

### US-5 作为团队，我希望这个坑不再回来

**AC-7 文案收口**
- 仓库内 `web/src` 不再出现「可不选」「可以先只选择会议」等暗示决议项可选的文案（`grep` 0 命中，含 `TaskFormDrawer.vue:518` 的 placeholder 与 `:210` 的 toast）；涉及「关联决议项」的 label/hint/toast 全部为必填口径。

**AC-8 回归用例与全量绿灯**
- 新增/扩展前端测试（建议 `web/tests/task-form-meeting-decision.spec.ts`，可复用 `web/tests/task-form-project.spec.ts` 的挂载与 `taskApi` mock 方式）覆盖 AC-1/2/3/4/5/6，**不少于 8 条用例**，且每条用「请求未发出 / 字段文案 / 载荷」这类可观察断言，不做实现细节断言。
- `web` 全量 `vitest run` 全绿（当前基线 174 条 + 新增）；`vue-tsc --noEmit` 通过；若本轮未改服务端，则 `server` 既有 247 条用例必须保持全绿（不改后端即不引入回归）。

**AC-9 真机闭环（18081 + 5174）**
- 按 1.1 步骤、使用 admin 与演示库：留空决议项保存 → 浏览器 Network 中**无** `POST /api/tasks`，字段行内提示可见且焦点落位；选上一条未转任务的决议项 → 保存成功，任务池出现该任务，详情来源显示「会议 + 决议项」。
- 证据：修复前后的保存动作录屏或截图 + Network 记录，落在任务夹说明中（不新增独立日志文件）。执行前先用会议详情确认目标决议项仍为「未转任务」；若已被前序手工测试消耗，改用其他未转任务决议项，禁止为此重置或改写演示库。

## 3. 范围与非目标

**范围**
- `web/src/components/task/TaskFormDrawer.vue`：会议形态「关联决议项」的必填标记、`validate()` 校验、`:invalid`/`:error` 绑定、`:ref` 注册、placeholder/hint/toast 文案、无可选项/加载失败/加载中的边界呈现；`applyServerErrors` 的定位通路复核。
- 新增/扩展前端测试（`web/tests/`），钉住「空决议项不可提交」「服务端 422 可定位」「三形态口径」「编辑态只读」。
- 只读核对：三形态前端必填集合 vs `TaskService.validateSource()`、`CreateTaskRequest` 的字段约束。

**非目标（本轮不做）**
- **不改后端**：`TaskService.validateSource()`、`CreateTaskRequest`、错误码、库层 CHECK 一律不动；不放宽「会议决议必须同时挂会议与决议项」的既定规则（Lead 已确认以服务端为准）。
- 不改 r1 的「一键转任务」入口、来源形态定义、三态互斥规则、编辑态不可改来源的设计。
- 不改任务池/矩阵/看板/日报/详情展示与任何统计口径；不迁移、不修补历史任务来源数据。
- 不重构抽屉表单框架，不引入表单校验库（保持现有 `form/errors/validate()` 模式）；不改 `AppSelect`/`AppSearchSelect` 的公共 API。
- 不做决议项的新建/编辑/删除能力，不改决议项「已转任务」判定逻辑。

## 4. 反面目标（anti-goals）

技术上跑通、测试全绿，但下面任意一条发生，人就会判定这次交付失败：

1. **用户仍然只看到一句「还有 1 项需要修改」**：点保存后底部有摘要，但「关联决议项」旁没有文案、焦点也不在该字段——这正是本次要消灭的现象，重现即失败。
2. **把用户困在无解表单里**：某会议决议项全部已转任务，界面仍允许选中它、允许填完标题/负责人/日期，直到点保存才被拦，且不说清「这个会议已没有可关联的决议项」。可观察：选中此类会议后、点保存前，界面必须已经说明不能保存的原因。
3. **编辑任务被牵连**：打开任一会议任务，只改标题点保存，却被要求重选决议项或被 422 拦下；或编辑态出现「必填未满足」的红字。
4. **只修了会议形态**：`PROJECT`/`NOTE` 的服务端 422（`sourceProjectId`/`sourceNote`）依旧只出底部摘要、字段无文案无焦点；或三形态的必填标记与后端校验对不上（例如说明形态 200 字上限只在一侧存在）。
5. **自作主张替用户绑定**：用户没有点选时表单自动填入唯一/第一条决议项并允许直接保存，导致连续建任务时绑错决议项。可观察：未手动选择时字段必须为空，提交必须被本地拦下。

## 5. 交互流程摘要

1. 打开新建任务抽屉：来源默认「会议决议」；「来源会议」「关联决议项」均带必填标记，决议项在未选会议时禁用、placeholder 为「请先选择来源会议」。
2. 选择来源会议：清空决议项并加载（`watch(form.meetingId)`，`:194-212`）；加载中 placeholder「决议项加载中…」；成功后列出未转任务项，已转任务项置灰不可选（`itemOptions`，`:160-168`）；若全部不可选 → 行内提示「该会议暂无可关联的决议项（均已成任务），请改选会议或改用其他来源」。
3. 选择决议项：带出标题/负责人/截止日期（用户已填的不覆盖）；清除该字段错误；底部摘要随之更新。
4. 点保存：本地 `validate()` 按形态产出错误顺序 → 摘要「还有 N 项需要填写」+ 每字段行内文案 + 焦点到首个错误；任一错误存在即不发请求。
5. 本地通过：按形态只提交自己那一组来源字段；服务端 201 → toast「任务已创建」→ 关闭抽屉并刷新列表。
6. 服务端 422（并发/数据过期等兜底）：摘要「还有 N 项需要修改」+ 服务端 `fieldErrors` 逐字段回填 + 焦点落首个字段；字段映射沿用 `SERVER_FIELD_MAP`。
7. 编辑态：来源整块只读（含决议项当前值），保存只提交标题/优先级；不进入上述必填校验。

## 7. 依赖与风险

**依赖**
- 服务端校验作为唯一权威口径（`TaskService.java:205-258`），本轮零改动；前端只对齐，不新增第三套规则。
- `AppSelect` 已支持 `required`/`:invalid`/`:error`/`:empty-text`（`meetingId` 与「来源项目」在用），无需改公共组件。
- 决议项接口 `taskApi.decisionItems(meetingId)` 返回项的 `converted` 标记（`:160-168` 已用于置灰），是「无可选项」判定的唯一来源。

**风险**
1. **把「必填」做成只改文案**：只删 placeholder、不接 `validate()`，用户仍被 422 拦。缓解：AC-1 以「0 次 POST + 行内文案 + 焦点」三重断言，AC-3 用表驱动锁死三形态。
2. **无可用决议项的会议变成死路**：会议可能因决议项全部转任务而无法再建会议任务，这会阻断正常业务。缓解：AC-6 要求保存前说明原因；策略本身属产品取舍，见「假设与待澄清」Q1。
3. **切换会议清空已选决议项**：`watch(form.meetingId)` 会重置选择，用户需重选；这是正确行为（防跨会议错绑），但可能被误报为 bug。缓解：保留清空逻辑，并在 AC-6 的提示中引导改选，不新增「记住上次选择」。
4. **测试只断实现不断行为**：断言 `required` 属性存在、断言内部变量，一改实现就红。缓解：AC-8 要求断言「请求未发出 / 页面文案 / 请求载荷 / 焦点」。
5. **真机数据被前序测试消耗**：演示库可关联决议项可能已被手工建任务占用。缓解：AC-9 执行前查会议详情，必要时换会议，不改库、不重置数据。
